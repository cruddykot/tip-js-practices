## 5. Задание 2 — модель задачи и создание

Поля задачи:

| Поле | Правило |
|---|---|
| `id` | Число, положительное безопасное целое: `Number.isSafeInteger(id)` и `id > 0`. |
| `title` | Строка; после `trim()` длина от 1 до 100. В объект записывается очищенная строка. |
| `completed` | Логическое значение. При создании всегда `false`. |
| `priority` | Одно из `"low"`, `"medium"`, `"high"`. По умолчанию `"medium"`. |

`createTask(id, title, priority = "medium")` возвращает `{ ok: true, task }`
при успехе и `{ ok: false, error: "..." }` при отказе. Типы проверяются
до ограничений; строковый `id` не преобразуется в число, `null` не заменяется
значением по умолчанию. Каждый успешный вызов создаёт новый объект задачи.

Проверено на всех обязательных случаях: границы длин 1 и 100, пустая строка
и строка из пробелов, длина 101, `title` типов `number` / `null` / `undefined`,
все недопустимые `id` (0, -1, 1.5, `"4"`, `NaN`, `Infinity`, `null`, `undefined`,
`Number.MAX_SAFE_INTEGER + 1`), верхняя граница `Number.MAX_SAFE_INTEGER`,
недопустимые приоритеты (`"urgent"`, `"HIGH"`, `" high "`, `null`, `1`),
два вызова с одинаковыми аргументами.

## 7. Задание 4 — добавление, изменение и удаление

Реализованы четыре функции изменения. Успех — `{ ok: true, tasks: новыйМассив }`,
ошибка — `{ ok: false, error: "..." }`. Во всех операциях `id` проверяется
по тем же правилам, что и в `createTask`.

| Операция | Правила |
|---|---|
| `addTask` | Создание через `createTask`, отказ при существующем `id`, добавление в конец нового массива. |
| `setTaskCompleted` | Принимает только `true` / `false`; меняет только `completed`. |
| `renameTask` | Проверяет и нормализует название; меняет только `title`; остальные поля сохраняются. |
| `removeTask` | Возвращает новый массив без выбранной записи, порядок сохраняется. |

**Требования к изменению данных выполнены:**

1. Входные массивы и объекты не мутируются ни при успехе, ни при ошибке.
2. Успешная операция возвращает новый массив.
3. Обновление создаёт новый объект выбранной задачи; остальные записи
   используются повторно без изменения.
4. Повторная установка того же статуса или названия — успех с новым массивом
   и новым объектом выбранной задачи.
5. Порядок элементов сохраняется; удаление не меняет `id` остальных.
6. Глобального изменяемого списка в модуле нет.

Использованы `[...tasks, newTask]`, `map` со spread объекта и `filter`.
`push`, `splice` и прямые присваивания свойствам входных объектов не применялись.

## 11. Вывод

По сравнению с ПР1 логика вынесена в отдельный модуль `task-service.js`;
данные хранятся в массиве объектов, а не в отдельных переменных. Все операции
возвращают результат в виде объекта с полем `ok`, а не пишут в консоль —
поэтому те же функции можно будет вызывать из браузерного интерфейса
без изменения прикладной части. Расчётные функции возвращают числа
и объекты, а форматирование (`toFixed`, «Задач пока нет») выполняется
только в `main.js`.

Отдельно проверено отсутствие мутации входных данных: создаётся новый
массив и новый объект только изменяемой записи. В `checks.js` это
подтверждено сценарием с `Object.freeze`.

Наиболее показательным оказался эксперимент 4 из задания 1: копия массива
через spread не защищает объекты внутри. Именно эту особенность пришлось
учесть в `setTaskCompleted` и `renameTask` — обновляется и массив, и объект
выбранной задачи.
